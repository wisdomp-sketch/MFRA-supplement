# Targeted Re-check Prompt (CR_V2)

You are performing a targeted re-check for conflict review.
You MUST output exactly one ReviewActionItem for the given tuple_id(s).

## Input
- original_text: the review text
- conflict_type: the conflict type for this tuple (if any)
- candidate_tuples: list of tuple objects with:
  - tuple_id
  - aspect_ref
  - aspect_term
  - polarity
  - evidence (may be null)
  - confidence (optional)
- prior_votes: actions from A/B/C (may be incomplete)

## Your task
Choose ONE action among: KEEP, DROP, FLIP, MERGE, FLAG.

### Hard constraints (format)
1) target_tuple_ids MUST be non-empty.
2) If action_type == FLIP: new_value MUST include {"polarity": "<positive|negative|neutral>"}.
3) If action_type == MERGE: new_value MUST include {"normalized_ref": "<valid_aspect_ref>"}.
4) If you cannot provide required fields, do NOT output FLIP/MERGE. Use FLAG with reason_code="FORMAT_INCOMPLETE".

### Decision guidance (do not over-generate)
- Prefer DROP when reason is structural redundancy and conflict_type indicates granularity overlap:
  - If conflict_type == "granularity_overlap_candidate" and an upper-level ref ("제품 전체#X") is redundant with a lower-level ref of same polarity, choose DROP with reason_code="REDUNDANT_UPPER_REF".
- Prefer FLIP only when polarity evidence is clear (negation/contrast scope etc.):
  - If negation/contrast is explicitly present and affects sentiment direction, FLIP with reason_code in {"NEGATION_SCOPE","CONTRAST_CLAUSE"}.
- Prefer MERGE only when ref normalization is unambiguous (e.g., duplicate refs or mapping within allowed taxonomy):
  - Use reason_code "SPAN_OVERLAP_MERGE" or "DUPLICATE_TUPLE" when applicable.
- If uncertainty remains:
  - Use FLAG. For granularity overlap use reason_code="REDUNDANT_REF_UNCERTAIN"; otherwise "TIE_UNRESOLVED" or "POLARITY_UNCERTAIN".

## Output schema
Return JSON matching:
{"review_actions":[{"action_type":"...","target_tuple_ids":["..."],"new_value":{...},"reason_code":"...","actor":"ARB"}]}

## KOREAN POLARITY POLICY — THREE LABELS

The polarity of each extracted record must be exactly one of:
"positive", "neutral", "negative".

- Select polarity from the sentiment expressed toward that record's
  target and category in context.

- Use "neutral" for content that qualifies as neutral under the
  Korean corpus annotation rules.

- Do not use "neutral" merely because you are uncertain, because
  the target is implicit, or because reviewers disagree.

- Use the existing confidence field, when available, to represent
  uncertainty without changing the meaning of the polarity label.

- Do not output "mixed", "unknown", or alternative polarity labels.

- Do not create a neutral record merely to avoid an empty output.
  A record must first satisfy the Korean annotation-scope rules.

- Preserve the Korean opinion segmentation rules. Do not automatically
  split every mixed expression into positive and negative records,
  or automatically collapse it into neutral.

- During review, do not reject a record solely because its polarity
  is neutral. Evaluate it using the ordinary evidence rules.

- When proposing a polarity change, specify the destination label
  through the existing action schema. Do not assume binary inversion.

## TERMINOLOGY

Use the following semantic terminology when reasoning:

- Target surface = aspect_term
  The explicit target expression that appears in the input text.
  If no explicit target is expressed, aspect_term="".

- Category = aspect_ref
  The normalized entity#attribute label selected from the closed taxonomy.

- Opinion expression = opinion_term
  The textual expression that conveys evaluation or sentiment.

- Polarity = polarity
  The sentiment directed toward the target/category pair.

When reviewing a candidate, interpret
(aspect_term, aspect_ref, polarity)
as
(target, category, polarity)
for one opinion record.

When writing JSON for the current stage, keep the native schema field names
(aspect_term, aspect_ref, polarity, opinion_term, …). Use the semantic terms
above for reasoning; write the target surface to aspect_term, the category to
aspect_ref, the opinion expression to opinion_term, and the polarity to polarity.
Do not rename schema keys in the output.
